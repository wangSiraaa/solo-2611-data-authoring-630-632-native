# 园区换接配电连接台账与电表事实仓（materials/630）

Python 3.11 标准库实现（SQLite + `fractions.Fraction`），无第三方依赖。
系统解决两个被旧实现混淆的问题：

1. **连接台账**把开关开合当作有版本的整组变更，按整组执行后的图判定合法性，
   并发布不可变、可重开查询的历史连接产品；预演完全不依赖电表。
2. **电表事实仓**独立解释模 M 累计计数器（绕回、换表、坏段、修订、撤回），
   查询时再与台账**已发布**的历史连接做时间交集；接线变更永远不是一条读数。

旧的 `network.py` / `meter_warehouse.py` / `example.json` 保留为起点，未被新代码依赖。

## 运行

```bash
cd materials/630
python3 run_scenarios.py                 # 六个复跑入口 + 两产品对照，41 项检查
python3 -m unittest tests.test_distgrid  # 26 个边界规则单测
python3 run_scenarios.py --keep-db --out-dir ./out   # 保留 SQLite 库以便人工检查
```

所有数据库都是普通文件；关闭后用 `DistGrid(path)`（不带 `setup`）重开，
产品、读数切面、查询记录原样可查。

## 关键规则如何落地

### 连接台账

- **整组判定**：`Topology.apply_actions` 先把一组动作用集合折叠成目标闭合边集，
  再调用一次 `evaluate`。“先合后开”的中间态从不参与判定，因此跨馈线换接不会被
  瞬时双馈线误拒；动作顺序不影响结果，同一边在一组动作里出现两次直接判输入非法。
- **完整重放**：每次提交都把候选版本与库内各变更的**头版本**合并，从 0 分钟初始图
  按分钟顺序重放全部当前变更；任一时点出现环或双馈线、或两个变更占同一分钟，
  整次请求拒绝，事务回滚，已发布产品哈希不变。
- **修订**：`(change_id, revision)` 为主键保留全部历史版本。低修订先做完整输入
  校验再忽略且不占分钟；同版同内容（动作按 `边→目标状态` 规范化，顺序无关）幂等重放，
  同版异文拒绝；高修订可改时点和动作，替换后从初始图完整重放。
- **历史产品**：`publish()` 对 `{设施, 全部变更身份与版本, 切片}` 求 SHA-256 得到
  `product_id`，产品规格整份入库。之后再修订只产生新产品，旧产品仍可 `state_at` /
  查询。输入边与动作顺序不改变同一历史的业务结果。

### 电表事实仓

- 读数点以 `(meter, point_no, revision)` 保存全部版本；点号固定归属一个电表，
  最高修订生效，撤回点带完整合法数据留在库中但离开有效集。
- 同批按输入序解释：同版冲突（即使后面还有更高版）整批拒绝；最终同表两个有效点
  不得占同一分钟；任何失败都在事务内回滚，不留半批。
- 段解释（只依赖相邻有效点与该表 M、R，与连接无关）：
  - 换表首点 `reset=True` 切断其**左侧**段，自身仍可作为下一段左端；
  - `R×gap ≥ M` 时绕圈次数不唯一 → **未知**，不猜圈数；
  - 否则电量取唯一非负模 M 差 `(v2-v1) mod M`；差超过 `R×gap` 为**坏段**；
  - 查询时 `gap > max_gap` 的整段判未知；首点之前、末点之后均未知。
- 正常段内按分钟线性分摊，全程使用 `Fraction` 精确有理数，序列化为分数字符串。
- 每个成功批次生成一个不可变**读数切面（cut）**；空库有 cut 0。查询可固定切面，
  更正过去读数只会追加新切面，旧切面与已返回结果不变。

### 查询（连续时间测度）

- 输入固定一个已发布 `product_id` 与一个 `cut_id`（默认最新），区间半开 `[start,end)`。
- 取连接切片分钟与读数段端点在查询窗内的并集作为切分边界，逐小区间判定：
  落在正常段内才计**已知**并按费率分摊给该分钟负荷所连馈线（断电负荷归
  `DISCONNECTED`）；其余（无相邻有效点、坏段、reset 断点、未知段、超 max_gap）
  一律计**未知时长**，绝不按零电量算已知。孤立端点不贡献时长。
- 每次查询的产品身份、切面、窗口、max_gap 求哈希得到 `query_id` 并落库；
  `verify_facet` 用同一对产品/切面重算并与存档逐字段比对。

## 六个复跑入口（`run_scenarios.py`）

1. 正常单馈线查询（含关闭重开后结果逐字段一致、有理数线性分摊）
2. 同一分钟换接（预演按整组放行、动作顺序幂等、重复边拒绝）
3. 非法双馈线整批拒绝（已发布产品不变、同版异文、低修订、同分钟冲突）
4. 累计值绕回（唯一模差可解释；不满足唯一性、坏段均计未知）
5. 换表（reset 切断左侧段、max_gap 整段未知）
6. 历史读数更正（新切面重算、旧切面与已返回查询不变、撤回保留与恢复）
7. 同组读数对照换接前后两个正式产品：真实产品改变归属；篡改产品内容与身份的
   绑定会被 `check_product_content` 显出错；明确请求旧产品合法。

## 状态组织为何能保证三类一致性，以及替代方案

**所选组织：仅追加（event-sourced）的版本事实 + 不可变快照 + 内容哈希身份。**

- 台账的 `changes` 与表仓的 `points` 都是**只追加**的版本行，当前投影永远通过
  “取每个身份的最高修订 → 从初始状态完整重放”得到，没有就地更新，因此插入/替换
  历史版本后全量重建的结果与长期运行对象必然相同，重开进程也无隐藏内存状态。
- 产品与读数切面是重放结果的**不可变快照**，身份即内容哈希。查询必须同时指名
  `product_id` 与 `cut_id`，三者一起哈希成 `query_id` 存档。更正读数或补插变更只
  追加新快照，旧快照不可变，所以“新查询重算、旧结果不变”是结构保证而非约定；
  消费者拿新身份却配旧内容时，哈希对不上即可被检出。
- SQLite 单库 + 事务提供串行写入和原子批次，失败回滚杜绝部分动作/半批读数。

**可行替代：在每张表上就地更新当前值（UPDATE-in-place），另用一张日志表留痕。**

- 好处是读取当前投影更快、表更小；但历史修订必须靠日志回放才能重建，一旦日志与
  当前表写入不在同一原子事务（或日志只记“新值”不记完整版本），重放结果可能与
  当时已发布的产品/切面漂移，无法证明“已返回结果不变”；同版异文、低修订忽略等
  规则也要额外加唯一约束和应用层补偿。本题规模（≤20 变更、≤200 点/表、≤10 表、
  全量重建）下，只追加 + 重放的成本可以忽略，而可证明的历史一致性正是题面核心，
  故选择前者。

## 约束与建模说明

- 时间/修订/M/R 均为非 bool 整数并按题面取值域校验；开关目标与 reset/retracted
  接受 0/1（含 bool）并规范化为整数。
- 设施 ≤12 节点、≤16 条已登记无向边；节点为馈线/接点/负荷；电表与负荷为 1:1 固定
  绑定（初始化后不可变）。未挂表的负荷在查询中整窗计未知，不会被当作零电量。
- 不做电力潮流计算、不接真实设备、无并行写入。
